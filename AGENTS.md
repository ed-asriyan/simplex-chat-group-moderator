# SimpleX Chat Group Moderator Bot — Agent Guide
Read this fully before making changes. It says what the project is and how work on it proceeds; how it is built is in [`docs/design.md`](docs/design.md).

## What this project is
A moderation bot for [SimpleX Chat](https://simplex.chat) groups, written in Rust (the crate lives in `bot/`), and its web editor (`webeditor/`). A group owner adds the bot to their group with the moderator role or higher; the bot then checks every member's message against the owner's rules and deletes the message, makes the author an observer or kicks them, as the rules say. The owner talks to the bot only in direct messages: `/groups` gives a link to the web editor, which carries the group's whole configuration — its mode and its rules — in the link's hash; the owner edits it in the browser and sends the updated link back. The full behaviour is specified in [`docs/user-stories.md`](docs/user-stories.md).

## Status
Implemented: the requirements are in `docs/user-stories.md`, the design in `docs/design.md`, the interface is the ports of the two bounded contexts, the rule types and the schema, and `bot/` and `webeditor/` implement it. The bot has unit tests for every condition, action, use case and adapter, though none cites a story yet; the end-to-end tests play every story that can be played from outside, the web editor's in a browser.

## How work proceeds
Every feature, however small, goes through the same stages, and each stage is reviewed by the maintainer before the next one starts:

1. **User stories.** Change the stories first, if the behaviour changes. They are a living document: they describe the current intended behaviour only; stories that no longer apply are removed, not kept as history (git has the history).
2. **User experience.** The web editor as the changed stories need it, built for real — every screen, element and state, with the stories' texts and its look finished, a new condition's or action's entry in `webeditor/rules-schema.json` included — with stubs behind what later stages write. The maintainer reviews it by using it and from its screenshots. A story played in the chat with the bot has no screen.
3. **End-to-end tests.** Each changed story played from the outside against the running system, with the points where the editor's screens are compared with their approved screenshots; they depend on the stories and the editor of stage 2 alone, so they come before the design, and they fail.
4. **Design.** The ports (traits and the value types they exchange), a new condition's or action's type, and the migration the stories need, and `docs/design.md` when the stories give a component a new responsibility or interaction, or need a new component — which most stories do not. Those files only: the rest of the code may stop compiling against the new ports. This is what the maintainer decides on; everything behind it is the later stages'.
5. **Unit tests.** The code compiles again with `todo!()` bodies where it no longer fits the ports, and unit tests are written against the ports and pure functions. They compile and fail.
6. **Implementation.** Code that makes the unit and end-to-end tests pass, screenshots ignored: the stubs of stage 2 filled and its temporary code removed, the editor otherwise as stage 2 built it.
7. **Finalize.** Every end-to-end test run with its screenshots compared: the screenshots the changed stories add or change are taken, judged against the stories and stage 2's review by a subagent, and shown to the maintainer; any other screen that changed is a regression, back to stage 6.

If a later stage needs to deviate from an earlier one, the earlier stage's artefact is updated in the same change, and the maintainer is told.

Write only what is true now, in the stories, the design, code comments and test names. When something is removed or renamed, delete every mention of it: never write that a command, rule or type "no longer exists", "was replaced by", "is gone" or "used to", and never explain a decision by the old state of things.

Each stage is a skill in `.claude/skills/`, started by the maintainer: `/stories`, `/ux`, `/e2e-tests`, `/design`, `/unit-tests`, `/implement`, `/finalize`; `/screenshots` shows the editor in the chat at any time. A skill does its own stage only, within the files it names, and stops for review; **never start the next stage on your own**, and never do a stage's work outside its skill. A stage with nothing to change says so instead of inventing work. `/coverage` checks, at any time, which stories the tests do not really cover. The skills hold nothing particular to this project: what they need from it is *Workflow*. They grew from a set the other projects started from too (see `.claude/skills/README.md`), and each project keeps its own copy: a change to the method rather than to this project is pointed out to the maintainer, who decides whether the other projects take it.

## Workflow
The project's values the stage skills use.

- **Stories:** `docs/user-stories.md`. A story id is `US-<epic letter><n>`, with an optional lower-case letter for a variant (`US-A1b`); its regex is `US-[A-Z][0-9]+[a-z]?`, and a story is defined as `**US-X1.**` at the start of its item. A bot story is written as the person sees the chat: what they send or do in SimpleX (`/groups`, an invitation with a role), then the bot's answer written out exactly, in its SimpleX Markdown. A condition or action story starts with what the owner sees when adding it in the editor — its title (**💬 Message Contains Any of These Words**) and its fields with their defaults and limits — then real settings, a message that matches or not, and the reason line the owner is told. An editor story names the controls as the editor labels them (*Apply changes*, *Copy the prompt*) and writes out what the owner reads. The examples use the owner, group and member of *Conventions* in the stories.
- **UX:** the web editor, `webeditor/`: `index.html`, `editor.css`, `editor.js`, `ai.js`, `transfer.js`, and `rules-schema.json`, from which it builds every condition's and action's fields, so a new one's entry there is the user interface's; the bot's chat has no screen, its texts are in the stories. It runs locally with `python3 -m http.server -d webeditor 8000`, at `http://localhost:8000/#bot_id=7&config=<lz>`, where `<lz>` is the group's configuration as JSON, compressed with lz-string's `compressToEncodedURIComponent`. A state is reached by its link: the configuration in the hash (no rules, a rule past the limits, a list of 150 entries), a link without `bot_id`, or one with unreadable settings; the rest by the steps a person takes on the page.
- **Stub body:** `todo!()`.
- **Schema snapshot:** the *Schema* section of `docs/design.md`, generated, never edited by hand: `cd bot && UPDATE_SCHEMA=1 cargo test schema` rewrites it, and the same test without the variable fails while it is out of date.
- **Tests:** a unit test cites its story as `// US-E1` above it, or `[US-E11]` in the file's doc comment; no test cites a story yet. A condition or action is tested in its own module's `tests.rs`; a use case through its inbound port with the fakes of `domain/moderator/application/tests.rs`; a storage adapter against the in-memory SQLite of `infrastructure/test_db.rs` (`test_db`). The architecture tests (`domain/architecture_tests.rs`, `domain/moderator/rules/architecture_tests.rs`) check the rules of `docs/design.md` on the source.
- **End-to-end tests:** the TypeScript Playwright project `e2e/`, which knows nothing of the bot's code; the tests are `e2e/tests/*.spec.ts`, one file per epic, each test citing its story as `// US-D2` above it. `e2e/harness/stack.ts` builds the images, starts them with `docker-compose.yml` overridden by `e2e/docker-compose.yml` — a SMP server of the stack's own, the bot and its SimpleX CLI with libfaketime in front of them, the web editor served at `http://127.0.0.1:18080` (the address the bot's links point to), and a SimpleX CLI for the people — reads the bot's address from its log, and moves the clock forward (`advance`); it never goes back, so a test never names a time. `Person` (`e2e/harness/person.ts`) is a user profile of that CLI: it talks to the bot, creates a group and invites the bot with a role, joins a group by its link, posts text, attachments and edits, changes roles, and sees in the group what a member sees (a message deleted, a role changed, being removed). The editor is used through Playwright's browser, by role and accessible name, and what it copies is read from the clipboard; the browser runs in Docker (`browser`, the image of the Playwright in `e2e/package.json`), so a page renders the same on every machine. **Screenshot tests:** where a story says what the owner sees in the editor, the test compares the page with its approved screenshot (`looks(page, 'apply-dialog')`, or a rule's pane for a condition's or action's fields), stored in `e2e/tests/__screenshots__/<project>/<spec>/<name>.png` and kept in **Git LFS** (`.gitattributes`); the projects are `computer` (1280×800, every spec) and `phone` (390×844, the editor's spec). A screenshot with nothing approved yet fails the test, everywhere. Stages 3 and 6 run the tests with `--ignore-snapshots`; `/finalize` takes the new ones with `--update-snapshots=missing` and takes one again with `--update-snapshots=changed -g '<test>'`. A toast is hidden while a screenshot is taken (`harness/screenshot.css`), as it leaves on a timer; `tests/helpers.ts` has the moderated group of *Conventions* (`scene`) and the owner's notification (`notice`). Tests share the stack and its clock, so they run one at a time, each from new people. The stack stays up after a run for a look at `docker compose -p simplex-chat-moderator-bot-e2e logs`, and is replaced at the next. `E2E_SKIP_BUILD=1` uses the images already built; `E2E_COMPOSE_FILES` adds compose files of the machine's own, `:`-separated (a kernel without IPv6 needs one, for the SMP server); `E2E_DEBUG=1` prints the people's events.
- **Not testable by nature:** by unit tests, the SimpleX driver, and the web editor, which the end-to-end tests cover instead; by end-to-end tests, US-B3 (a failure inside the bot cannot be caused from outside), and whatever needs an AI provider to answer: US-C4, the verdicts of US-E25 and US-E26, and when US-E27 asks them.
- **Only the implementation writes:** the bot's texts (`domain/bot_dm/application.rs`): they are never stubbed. The web editor's code is written by `/ux`, and its stubs filled by `/implement`.
- **Commands**, from `bot/`: build `cargo build --all-targets`; compile the tests `cargo test --no-run`; test `cargo test`; lint `cargo clippy`. End-to-end, from `e2e/` (needs Docker, Node and Git LFS): `npm ci`, then `npx playwright test`; type-check `npx tsc -p .`. The approved screenshots are Git LFS files: a clone made without Git LFS set up (`git lfs install` never run on the machine, as in a fresh container) holds small text pointers in their place, and every screenshot test fails as if the screen had changed (a PNG that cannot be read, or one of a few hundred bytes). The clone is then mended with `git lfs install --local && git lfs pull`, never by taking the screenshots again; a new or changed one is committed with Git LFS set up, so it goes in as an LFS file (`git lfs ls-files` lists it). CI checks out with `lfs: true`. Coverage, from the repository root: `.claude/skills/coverage/scripts/story_coverage.sh docs/user-stories.md 'US-[A-Z][0-9]+[a-z]?' unit=bot/src:tests.rs 'e2e=e2e/tests:*.spec.ts'`.

## Language
Everything committed to this repository is in **English** — code, comments, docs, commit messages — regardless of the language the conversation with the maintainer happens in. The bot and the editor speak English only.

## Design
[`docs/design.md`](docs/design.md) is how the bot and the editor are built: the architecture and the rules it sets (checked by the architecture tests), the two bounded contexts (`bot_dm` and `moderator`) and the web editor with what each is responsible for and interacts with, where code goes, the steps for adding a condition or an action type, and the schema. Read it before changing code; its rules hold for every change, inside a stage or not.

## Migrations
The schema is changed by migrations in `bot/src/infrastructure/migrations/`, and the whole current schema is generated from them into `docs/design.md` *Schema* (*Workflow*); its conventions are in `docs/design.md` (*Persistence*).

- Files are named `NNNN_description.sql` (zero-padded, sequential). They are embedded at build time and applied in **filename sort order**.
- The applied version is tracked in SQLite's `PRAGMA user_version`; the runner (`infrastructure/migrations.rs`) skips already-applied files and runs each remaining file in its own transaction, then bumps `user_version`. The version is the file's 1-based position in the sorted list, so **never reorder, rename, renumber, or delete an existing migration file.**
- `PRAGMA foreign_keys = ON` is set for the connection, so `ON DELETE CASCADE` and FK constraints are enforced during migrations and at runtime.
- **Immutability rule:** once a migration has been merged to `master` it is **released** (see *Deployment*). Treat released migrations as frozen and add a **new** numbered migration to change the schema. Editing a migration in place is only acceptable while it is still unreleased (not yet on `master`) and has not run against any real database.
- When restructuring tables, include a data **backfill** in the same migration and drop old tables **children before parents** so FK enforcement stays satisfied.

## General conventions
- Async traits use `#[async_trait]`.
- Convert errors and types **at boundaries** (adapters/routers), not inside the domain.
- A module's doc comment (`//!`) says what its code cannot: the rule it keeps that its callers rely on, the outside constraint it works around (a messenger's limit, an API's behaviour), why it is built the way it is. It cites the stories it serves. It does not retell the code.
- Keep tests in separate files (e.g. `#[cfg(test)] mod tests;` pointing to `<module_name>/tests.rs` or `<module_dir>/tests.rs`), never inline in implementation files.
- Keep changes minimal and within the established structure; if a change seems to require breaking one of the hard rules in `docs/design.md`, stop and ask rather than working around it.

## Deployment
Every commit to `master` is the release: CI/CD builds and deploys the **bot** to production and publishes the `webeditor/` folder to **GitHub Pages**. There is no separate release step — merging to `master` ships to production. This is why a migration counts as released (and therefore frozen) the moment it lands on `master`.
